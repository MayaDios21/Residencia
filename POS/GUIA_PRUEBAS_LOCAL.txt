GUIA DE PRUEBAS LOCALES
PUNTO DE VENTA - TACOS DE BIRRIA EL COMPITA

Esta guia explica como levantar el proyecto localmente para hacer pruebas.
Se necesitan dos terminales abiertas al mismo tiempo:

  1. Una para el backend de Django.
  2. Otra para el servidor del frontend.


1. UBICACION DEL PROYECTO

Abrir PowerShell y entrar a:

  cd C:\Users\dmaya\Residencia\POS


2. PREPARAR EL ENTORNO (SOLO LA PRIMERA VEZ)

Si existe el entorno virtual del proyecto, activarlo:

  .\.venv\Scripts\Activate.ps1

Si PowerShell bloquea la activacion, usar este comando solo para la terminal actual:

  Set-ExecutionPolicy -Scope Process -ExecutionPolicy RemoteSigned
  .\.venv\Scripts\Activate.ps1

Si no existe .venv, crear el entorno:

  py -m venv .venv
  .\.venv\Scripts\Activate.ps1

Instalar las dependencias del backend:

  cd C:\Users\dmaya\Residencia\POS\BakcEnd
  python -m pip install -r requirements.txt


3. PREPARAR LA BASE DE DATOS LOCAL

La version local utiliza SQLite. La base de datos se crea en:

  BakcEnd\db.sqlite3

Aplicar las migraciones:

  python manage.py migrate

Cada vez que se descarguen cambios del repositorio (git pull) que incluyan
archivos nuevos en BakcEnd\pos\migrations, volver a ejecutar:

  python manage.py migrate

La base db.sqlite3 es local y esta excluida de Git. Cada integrante debe
crear sus propios usuarios en su computadora.

Para validar PostgreSQL en desarrollo, configurar `DATABASE_URL` en la
terminal del backend antes de ejecutar Django. No escribir credenciales reales
en `.env.example` ni subir un archivo `.env`:

  $env:DATABASE_URL="postgresql://USUARIO:CONTRASENA@HOST:5432/NOMBRE_BD"

Con `DATABASE_URL` definido, Django usa PostgreSQL automáticamente. Sin esa
variable, continúa usando SQLite como respaldo local.

Después de configurar una instancia PostgreSQL accesible, ejecutar desde
`C:\Users\dmaya\Residencia\POS\BakcEnd`:

  python manage.py check
  python manage.py migrate
  python manage.py test pos

La migración definitiva de los datos existentes de SQLite no forma parte de
esta validación temprana; primero se comprueba que el esquema y el código sean
compatibles con PostgreSQL.

5. INICIAR EL BACKEND - TERMINAL 1

Desde:

  C:\Users\dmaya\Residencia\POS\BakcEnd

Ejecutar:

  $env:DJANGO_SECRET_KEY="local-development-key"
  $env:DJANGO_DEBUG="True"
  python manage.py runserver 127.0.0.1:8000

DJANGO_DEBUG="True" es necesario en desarrollo: por seguridad, si no se
define, Django arranca en modo produccion (sin paginas de error detalladas,
sin estilos en /admin/ y sin la API navegable).

La terminal debe mostrar:

  Starting development server at http://127.0.0.1:8000/

No cerrar esta terminal ni presionar Ctrl+C mientras se hagan pruebas.


6. INICIAR EL FRONTEND - TERMINAL 2

Abrir otra terminal de PowerShell y ejecutar:

  cd C:\Users\dmaya\Residencia\POS
  .\.venv\Scripts\Activate.ps1
  python -m http.server 8080 --directory C:\Users\dmaya\Residencia\POS

La terminal debe mostrar:

  Serving HTTP on :: port 8080

No ejecutar el servidor desde la carpeta FronEnd. Debe iniciarse desde la
raiz POS para que tambien se sirvan las imagenes de la carpeta Public.

8. PRUEBAS RECOMENDADAS

Administrador:

  - Iniciar sesion.
  - Revisar el panel.
  - Revisar productos, categorias, almacen y configuracion.
  - Cerrar sesion.

Backend desde el navegador (API navegable):

  Mientras USE_API sea false en el archivo FronEnd\js\api.js, las pantallas
  del sistema (Almacen, Caja, Venta, Configuracion) guardan solo en el
  navegador. Para probar lo que se guarda en la base de datos se usa la
  API navegable de Django, que solo funciona con DJANGO_DEBUG=True.

  Preparacion:

  - Entrar a http://127.0.0.1:8000/admin/ con admin / 1234.
  - En "Productos", crear un producto de prueba (nombre y precio) y marcar
    "Controlar en almacen" (solo los productos por pieza, como refrescos,
    llevan inventario; la comida no). El stock no se edita aqui: empieza
    "sin registrar".
  - Sin cerrar esa pestaña, abrir las direcciones de abajo. Cada una
    muestra los datos y, al final, un formulario. En los que piden JSON,
    usar la pestaña "Raw data", pegar el texto y presionar POST o PATCH.

  Inventario (Fase 1) - http://127.0.0.1:8000/api/inventario/movimientos/

    {"product_id": 1, "type": "entrada", "quantity": 10, "reason": "Compra"}

    Cambiar el 1 por el id del producto. Probar tambien "salida" y
    "ajuste" (el ajuste fija el stock al numero indicado). Una salida
    mayor al stock debe responder 409. Un producto sin "Controlar en
    almacen" responde 400.

  Configuracion (Fase 2) - http://127.0.0.1:8000/api/configuracion/

    Ver IVA (tax_rate, 0.0800 = 8 %) y tipo de cambio. Para cambiarlos,
    PATCH con, por ejemplo:

    {"tax_rate": "0.16", "exchange_rate": "18.50"}

    Valores fuera de rango (IVA mayor a 1 o tipo de cambio 0) responden 400.

  Caja y ventas (Fase 2), en este orden:

    1. http://127.0.0.1:8000/api/caja/actual/
       Debe decir "status": "sin_abrir".
    2. http://127.0.0.1:8000/api/ventas/
       POST con lo de abajo: debe responder 409 porque la caja no esta abierta.

       {"items": [{"product_id": 1, "quantity": 2}], "payment": "Efectivo"}

    3. http://127.0.0.1:8000/api/caja/abrir/
       Escribir el fondo inicial (por ejemplo 500) y presionar POST.
    4. Repetir la venta del paso 2: ahora responde 201 con subtotal, IVA,
       total calculados por el servidor y "stock_remaining" del producto.
       Una venta con mas piezas que el stock debe responder 409.
    5. http://127.0.0.1:8000/api/caja/actual/
       Debe decir "abierta" y mostrar las ventas del dia.
    6. http://127.0.0.1:8000/api/caja/cerrar/
       POST (los campos son opcionales; si se dejan vacios el efectivo
       contado se toma igual al esperado). Revisar expected_cash =
       fondo inicial + ventas del dia - gastos menores.
    7. Intentar otra venta o abrir otra caja: ambas deben responder 409.
    8. http://127.0.0.1:8000/api/caja/cierres/ y
       http://127.0.0.1:8000/api/caja/cierres/exportar/ (descarga un CSV).

  Historial de ventas (Fase 3):

    Hacer estas pruebas con la caja ABIERTA (entre los pasos 4 y 6 de
    arriba), porque una venta solo se puede cancelar mientras su jornada
    sigue abierta. Registrar antes 2 o 3 ventas.

    1. http://127.0.0.1:8000/api/ventas/
       Lista las ventas, la mas reciente primero, con sus productos,
       "items_count" (articulos) y estado.
    2. Filtros (se agregan al final de la direccion):
         ?desde=2026-10-20&hasta=2026-10-20   rango de fechas (AAAA-MM-DD)
         ?q=taco                              busca por producto
         ?q=3                                 busca la venta #3
         ?estado=cancelada                    abierta, cerrada o cancelada
       Una fecha mal escrita responde 400.
    3. http://127.0.0.1:8000/api/ventas/1/
       Detalle de una venta (cambiar el 1 por el numero de venta).
    4. http://127.0.0.1:8000/api/ventas/resumen/
       Total vendido, transacciones, articulos y promedio (las tarjetas
       del historial). Acepta los mismos filtros. No cuenta canceladas.
    5. http://127.0.0.1:8000/api/ventas/exportar/
       Descarga ventas.csv (acepta los mismos filtros).
    6. http://127.0.0.1:8000/api/ventas/verificar/
       Revisa que los montos de cada venta cuadren. Debe decir
       "with_errors": 0.
    7. http://127.0.0.1:8000/api/ventas/1/cancelar/
       POST con un motivo opcional, por ejemplo:

         {"reason": "Error de captura"}

       La venta queda "cancelada", el stock del producto regresa (revisar
       en /api/inventario/movimientos/ un movimiento "cancelacion") y deja
       de contar en el resumen y en el cierre de caja. Cancelarla otra vez,
       o cancelar una venta de una jornada ya cerrada, responde 409.
    8. Entrar como cajero: el cajero solo ve las ventas de hoy y no puede
       verificar ni cancelar (responde 403). Para cambiar de usuario, cerrar
       sesion en /admin/ y entrar con cajero; si cajero no tiene acceso al
       panel, darselo con:

         python manage.py shell -c "from django.contrib.auth.models import User; User.objects.filter(username='cajero').update(is_staff=True)"

    Las ventas ya no se borran: el boton "Borrar historial" del sistema
    solo limpia el navegador mientras USE_API sea false. En la base de datos
    las ventas se cancelan, para que quede registro.

  Usuarios (Fase 4) - en el sistema, no en la API navegable:

    Esta pantalla SI usa el backend aunque USE_API sea false, porque los
    usuarios solo existen en la base de datos (igual que el inicio de sesion).

    1. Abrir http://127.0.0.1:8080/FronEnd/index.html y entrar como
       Administrador (admin / 1234). Debe aparecer la pestaña "Usuarios".
    2. Agregar usuario: llenar el formulario con rol Cajero. Probar primero
       la contraseña 1234: debe rechazarla (minimo 8 caracteres, no solo
       numeros, no comun). Luego usar una como Birria-Compita-2026.
    3. Cerrar sesion y entrar con el usuario nuevo como Cajero: debe
       funcionar y NO debe ver la pestaña Usuarios.
    4. Volver como admin y probar en la tabla:
         - "Hacer administrador" / "Hacer cajero": cambia el rol y obliga a
           ese usuario a iniciar sesion de nuevo.
         - "Desactivar": ya no puede iniciar sesion. Con "Mostrar inactivos"
           se ve en la lista y se puede "Activar" otra vez.
         - En la fila propia (tú) los botones estan deshabilitados: nadie
           puede desactivarse ni quitarse el rol de administrador.
    5. Restablecer contraseña: elegir el usuario y escribir la nueva dos
       veces. Si se elige la propia cuenta, el sistema cierra la sesion para
       entrar con la nueva.
    6. Los usuarios no se borran. Para borrar los de prueba en la base local,
       desde BakcEnd (cambiar "nombre" por el usuario):

         python manage.py shell -c "from django.contrib.auth.models import User; User.objects.filter(username='nombre').delete()"

       Si ese usuario ya registro ventas, cajas o movimientos, Django no lo
       deja borrar; en ese caso solo desactivarlo.

    Nota: admin y cajero usan 1234 porque se crearon con los comandos de la
    seccion 4; las reglas de contraseña solo aplican a cuentas creadas o
    cambiadas desde el sistema.

  Insumos, alertas y reportes (Fase 5):

    Insumos (vasos, platos, cucharas… cosas que no se venden):

    1. http://127.0.0.1:8000/api/inventario/insumos/
       POST para crear uno:

         {"name": "Vasos desechables", "minimum_stock": 50}

    2. Darle stock con un movimiento en /api/inventario/movimientos/
       (igual que un producto, pero con supply_id en vez de product_id):

         {"supply_id": 1, "type": "entrada", "quantity": 60}

       Registrar el uso diario como "salida". Un insumo con movimientos no
       se borra (409): se desactiva con {"is_active": false}.

    Alertas de stock y algoritmo de reabastecimiento:

    3. http://127.0.0.1:8000/api/inventario/alertas/
       Muestra los productos controlados en almacen y los insumos que
       necesitan atencion, los mas urgentes primero. Por cada uno:
         - consumed: piezas que salieron en los ultimos 14 dias
           (ventas + salidas - cancelaciones).
         - daily_average: consumo promedio por dia.
         - coverage_days: para cuantos dias alcanza el stock actual.
         - suggested_quantity: cuanto pedir para cubrir los 2 dias que
           tarda un pedido y quedar en el minimo.
         - level: "critico" (sin stock o se acaba antes de que llegue el
           pedido), "bajo" (en el minimo o debajo), "sin_registrar"
           (nunca se conto) u "ok".
       Agregar ?todos=true para ver tambien los que estan bien,
       ?dias=30 para promediar 30 dias o ?reposicion=3 si el pedido tarda
       3 dias.

    Reportes del panel (no cuentan ventas canceladas; aceptan
    ?desde=AAAA-MM-DD&hasta=AAAA-MM-DD):

    4. http://127.0.0.1:8000/api/reportes/resumen/
       Total vendido, IVA, transacciones, articulos y ticket promedio.
    5. http://127.0.0.1:8000/api/reportes/ventas-por-dia/
       Total por dia (por defecto los ultimos 7 dias; los dias sin ventas
       salen en 0).
    6. http://127.0.0.1:8000/api/reportes/productos-top/
       Productos mas vendidos por piezas (?limite=5 para ver solo 5).
    7. http://127.0.0.1:8000/api/reportes/por-categoria/
       Ventas por categoria.

    Alertas y reportes son solo para el administrador: el cajero recibe 403.

  En el panel /admin/ se pueden consultar Ventas, Jornadas de caja,
  Movimientos de inventario y Configuracion. Ventas, cajas y movimientos
  son de solo lectura: se registran por la API para que el stock y los
  totales siempre se calculen bien.

  IMPORTANTE: solo se permite una caja por dia. Si se cierra la caja de
  hoy durante las pruebas, ya no se podra abrir otra hasta mañana. Para
  reiniciar las pruebas en la base local (borra cajas, ventas y
  movimientos, no productos ni usuarios), desde BakcEnd:

    python manage.py shell -c "from pos.models import *; InventoryMovement.objects.all().delete(); SaleItem.objects.all().delete(); Sale.objects.all().delete(); CashSession.objects.all().delete(); Product.objects.update(stock=None)"

  En la pestaña Almacen del sistema, un "Ajuste de inventario" fija el
  stock al numero escrito (no lo resta).

Cajero:

  - Iniciar sesion.
  - Abrir la caja con un fondo inicial mayor que cero.
  - Agregar productos al carrito.
  - Revisar subtotal, IVA y total.
  - Registrar una venta.
  - Revisar el historial.
  - Cerrar la caja.

10. PROBLEMAS COMUNES

Mensaje "Failed to fetch":

  - Confirmar que Django este corriendo en el puerto 8000.
  - Confirmar que Edge use la URL http://127.0.0.1:8080/FronEnd/index.html.
  - No usar file:///.

No aparecen las imagenes:

  - Detener el servidor del frontend con Ctrl+C.
  - Volver a iniciarlo desde C:\Users\dmaya\Residencia\POS.
  - Usar:

      python -m http.server 8080 --directory C:\Users\dmaya\Residencia\POS

Credenciales incorrectas:

  - Ejecutar nuevamente los comandos de la seccion 4.
  - Por seguridad, el mensaje es el mismo si falla el usuario o la
    contraseña, para no revelar cual de los dos estaba mal.

"Demasiados intentos fallidos. Espera un minuto":

  - Tras 5 intentos fallidos en un minuto desde la misma computadora, el
    inicio de sesion se bloquea un minuto (protege contra quien intenta
    adivinar contraseñas). Esperar un minuto, o reiniciar el backend
    (Ctrl+C y volver a ejecutar runserver) para limpiar el contador.
  - Los inicios de sesion correctos no cuentan para el limite.

El puerto ya esta ocupado:

  - Cerrar el servidor anterior con Ctrl+C.
  - Si la terminal anterior ya no existe, cerrar el proceso que este usando
    el puerto o reiniciar VS Code.


11. VALIDAR EL BACKEND SIN ABRIR EL FRONTEND

Desde BakcEnd ejecutar:

  python manage.py check

El resultado esperado es:

  OK

IMPORTANTE

No subir al repositorio:

  - .env
  - db.sqlite3
  - carpetas __pycache__
  - contraseñas reales
  - tokens

El archivo .env.example si se puede subir porque solo contiene nombres y
valores de ejemplo.
